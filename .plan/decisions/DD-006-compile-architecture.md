## 决定

编译器从架构设计第一天起采用细粒度查询式缓存（Salsa 模式）作为核心架构，而非后期补丁式优化。增量编译颗粒度精确到函数级别。泛型单态化在整个项目范围内全局去重，并提供 `dyn_generic` 显式逃生舱应对代码体积膨胀问题。

## 背景与问题

Rust 的增量编译系统是**后期引入的补丁**（基于 Salsa 查询框架思想），而非从一开始的架构设计。这导致：

1. 增量编译粒度相对粗，查询系统与原有编译流程的融合存在历史包袱
2. **单态化膨胀（Monomorphization Bloat）**是 Rust 编译慢的头号真凶之一：相同泛型实例可能在不同 crate 中被重复编译

Leaves 希望从架构设计之初就把细粒度查询缓存作为一等公民，并针对性解决单态化膨胀问题。

## 采纳方案

### 查询式架构

```
传统编译流程（Leaves 摒弃）：
  源文件变化 → 整个模块重新编译 → 链接

Leaves 查询式编译：
  每个函数/类型签名 = 独立查询节点
  修改一个函数体 → 仅该函数及其直接依赖者重新编译
  未受影响的函数直接复用缓存结果
```

修改函数体（非签名）时，依赖该函数的其他模块无需重新编译，只有该函数自身重新走查询流程。

### 单态化全局去重

整个项目作为统一编译会话，相同泛型实例化（如多个模块都用到 `Vec<i32>::push`）只编译一次。

### dyn_generic 显式逃生舱

```lv
// 默认：单态化（zero-cost，但编译时间/体积成本随实例增多而增加）
function process<T: Clone>(x: T) -> T { x.clone() }

// 显式选择：动态分派（字典传递，牺牲少量运行时性能换取编译速度与体积）
function process<T: Clone>(x: T) -> T dyn_generic {
    x.clone()
}
```

### 规则细节

- 编译器测量泛型实例化次数/预计体积，超过阈值时**主动提示建议**（非自动切换）：

```
warning: 泛型函数 `process<T>` 在当前项目中被实例化了 47 次，
         预计增加约 230KB 编译产物体积。

hint: 考虑添加 `dyn_generic` 标记以减少二进制体积
      (此提示阈值可在 Leaves.toml 中配置: monomorphization_warn_threshold = 20)
```

- **不做自动切换**：静默改变代码性能特征（单态化→动态分派）属于语义层面变化，违背"显式优于隐式"原则，决策权始终留给开发者

### 技术栈选型

- 实现语言：Rust
- 解析策略：手写递归下降 + Pratt 解析（优先错误恢复质量，优于生成式解析器）
- 增量计算框架：`salsa` crate（rust-analyzer 同款方案）
- 后端：LLVM（`inkwell` 绑定）

## 被否决的备选方案

| 方案                                             | 为什么被否决                                                                               |
| ------------------------------------------------ | ------------------------------------------------------------------------------------------ |
| 沿用传统线性编译管道，增量编译作为后期优化       | 重蹈 Rust 的历史包袱，无法实现函数级别的精细缓存颗粒度                                     |
| 泛型单态化不做去重，依赖后期链接器优化（如 LTO） | 无法从根本解决编译时间问题，链接器优化发生在编译完成之后，无法避免重复编译的前期开销       |
| 超过阈值自动切换为动态泛型                       | 违反"显式优于隐式"的核心设计哲学，静默改变代码性能特征可能让开发者困惑或遇到意外的性能退化 |
| 自己实现查询缓存框架，不依赖 salsa               | 增加不必要的自研成本和风险，salsa 已经过 rust-analyzer 大规模生产验证                      |

## 影响范围

- 整个编译器架构的核心骨架，影响所有后续编译阶段的实现方式
- 与 DD-005（模块系统）的目录结构密切配合，决定查询缓存的失效边界
- 与 DD-004（dyn_generic）存在交互，需要明确两套分发机制在编译器内部的关系

## 验证方式

- Phase 2 阶段评估 `salsa` crate 与 Leaves 查询设计的适配性，产出技术选型文档
- Phase 4 阶段在真实多模块项目上测量增量编译性能，验证"修改函数体不影响未依赖模块"的核心承诺
