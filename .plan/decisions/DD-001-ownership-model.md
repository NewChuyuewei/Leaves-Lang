## 决定

Leaves 采用所有权系统（Ownership System）进行内存管理，不使用垃圾回收（GC），不使用引用计数作为默认机制。

## 背景与问题

Leaves 的核心定位是"极致性能 + 安全"，面向软件工程、游戏开发等对性能和内存可预测性有较高要求的场景。

- **GC 的问题**：停顿不可预测，不适合游戏开发等实时系统；运行时开销持续存在
- **纯手动管理的问题**：安全性不达标，与"安全"的核心定位冲突
- **需要的是**：编译期保证内存安全，且无运行时开销的方案

## 采纳方案

参考 Rust 的所有权模型：

- 每个值在任意时刻有且仅有一个所有者（owner）
- 所有者离开作用域时，值被自动释放（drop）
- 值可以被**移动**（move）转移所有权，移动后原变量不可再使用
- 值可以被**借用**（borrow）产生引用，受借用检查规则约束（可变借用唯一、不可变借用可多个、借用不可超过被借用值的生命周期）

### 规则细节

- 默认移动语义（非拷贝类型赋值/传参即转移所有权）
- 实现 `Copy` 标记的类型按值复制而非移动（基础类型默认 Copy）
- 借用检查规则与 Rust 基本一致，具体推断策略见 DD-002
- 不提供默认的引用计数包装类型作为"逃避所有权思考"的捷径；`Rc`/`Arc` 等价物作为标准库中的**显式选择**存在，但语言核心语义不依赖它们

## 被否决的备选方案

| 方案                                 | 为什么被否决                                                                         |
| ------------------------------------ | ------------------------------------------------------------------------------------ |
| 纯 GC（类 Go）                       | 停顿不可预测，无法满足游戏开发实时性要求；与"极致性能"定位冲突                       |
| ARC 自动引用计数（类 Swift）         | 循环引用问题依然存在，需要额外的 weak 引用处理；仍有运行时开销（引用计数的原子操作） |
| 纯手动管理（类 C）                   | 安全性无法达标，不符合"安全"核心定位；容易产生悬垂指针/内存泄漏                      |
| 混合模式（默认GC，关键路径手动管理） | 语义不统一，心智负担反而更重；两套内存模型并存会让借用检查器设计复杂度剧增           |

## 影响范围

- 类型系统：Copy/Move 语义是类型的基本属性
- 借用检查器：是整个编译器中最核心、最复杂的子系统
- Region 系统（DD-003）直接建立在所有权模型之上，是其自然扩展
- 并发模型（DD-007）的 Channel 设计依赖所有权转移语义

## 验证方式

- 通过 Phase 3 MVP 编译器的借用检查器初步实现验证基础可行性
- Rust 已经证明这套模型在工业界可行，Leaves 的验证重点在于 DD-002/DD-003 的改进是否破坏了原有的安全保证
