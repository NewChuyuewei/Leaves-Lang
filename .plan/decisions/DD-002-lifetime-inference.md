## 决定

Leaves 采用两级生命周期推断策略：

1. **第一级（扩展版签名推断）**：适用于所有函数（含 `pub`），在 Rust 现有省略规则基础上扩展，覆盖更多常见模式
2. **第二级（函数体流分析）**：仅适用于非 `pub`（私有/内部）函数，通过分析函数体的借用溯源，自动推断生命周期约束

`pub` 可见性函数必须保持**签名自洽**——其生命周期关系完全由签名本身确定，不依赖函数体实现，以保证 API 稳定性。

## 背景与问题

Rust 现有的生命周期省略规则（Lifetime Elision）只有 3 条，且刻意**不分析函数体**，这是为了保证 API 稳定性（库作者修改内部实现不应意外改变外部契约）。

但这个限制对**私有函数**是不必要的严格——私有函数的调用者都在同一编译单元内，签名变化会被编译器一并检查到，不存在"意外破坏外部契约"的风险。

Rust 这种一刀切的保守策略，导致大量日常代码（尤其是内部辅助函数）被迫写出不必要的生命周期标注，这是 Leaves 要解决的核心工程体验问题。

## 采纳方案

### 第一级：扩展版签名推断（所有函数生效）

在 Rust 原有 3 条规则基础上新增：

**规则 A：结构体字段自动生命周期**

```lv
// 无需手写 <'a>，编译器自动生成
struct Foo {
    field: &str,
}
```

**规则 B（已关闭，见下方说明）**：多参数同类型自动假设同源生命周期 —— 此规则**默认关闭**，避免引入"隐式假设"增加理解负担。如需要这种效果，必须用第二级推断（私有函数）或显式标注（公开函数）。

### 第二级：函数体流分析（仅私有/内部函数）

```lv
// 私有函数，编译器分析所有 return 路径，自动推断返回值的借用来源
function pick_one(a: &Data, b: &Data, use_first: bool) -> &Data {
    if use_first { return a; } else { return b; }
}
```

算法步骤：

1. 遍历函数体所有 `return` 路径
2. 对每条路径做数据流追踪，确定返回值借用来源（参数/新分配/字面量）
3. 若所有路径来源可统一 → 自动生成生命周期约束
4. 若来源冲突（如某分支返回局部变量引用）→ 编译期报错，并指出具体冲突路径

### 兜底：显式标注

当以上两级都无法消除歧义，要求显式标注，且**编译器错误信息必须包含具体代码路径与可操作的修改建议**（这是与 Rust 报错体验的核心差异化点）。

### 规则细节

- 结构体字段引用：自动生成生命周期参数（规则A）
- 多参数同类型：**不**自动假设同源（规则B默认关闭）
- 私有函数：启用函数体流分析（borrow provenance analysis）
- `pub` 函数：仅第一级规则生效，必须签名自洽，不读函数体
- 显式标注的具体语法：**待定，见 OQ-007**，需要在 Phase 1 优先解决

## 被否决的备选方案

| 方案                                       | 为什么被否决                                                                                                        |
| ------------------------------------------ | ------------------------------------------------------------------------------------------------------------------- |
| 完全自动推断，不支持显式标注               | 复杂场景（如真正的双向依赖）必然存在无法静态消歧的情况，完全不支持标注会导致部分合法程序无法表达                    |
| 用"区域"（Region）概念完全替代生命周期标注 | 这个思路被保留并发展为独立的 DD-003，但不能完全替代函数签名层面的生命周期表达，两者是互补而非替代关系               |
| 规则B（多参数同类型自动假设同源）默认开启  | 这是一种语义假设而非纯语法规则，可能让新手难以理解"为什么这样会报错/不报错"的隐式逻辑，违反"显式优于隐式"的核心哲学 |
| pub 函数也启用函数体流分析                 | 会破坏 API 稳定性保证，库作者修改内部实现可能意外改变调用者看到的生命周期契约                                       |

## 影响范围

- 类型系统的核心复杂度来源之一
- 直接影响借用检查器的实现架构（需要支持两种不同深度的分析）
- 影响标准库 API 设计风格（公开 API 需要考虑签名自洽的限制）

## 验证方式

- 需要用 `.plan/examples/` 中的真实场景（尤其是 Rust 中常见需要生命周期标注的模式）逐一验证推断效果
- Phase 3 MVP 阶段实现第一级规则，Phase 4 实现第二级规则，分阶段验证可行性
