## 决定

Leaves 的模块边界由文件系统目录结构自动确定，取消 Rust 式手动 `mod xxx;` 声明。可见性简化为三级。模块间依赖规则：同一目录内文件允许互相循环引用，跨目录模块间强制有向无环图（DAG），禁止循环依赖。

## 背景与问题

Rust 模块系统的痛点：

1. **mod 声明的仪式感**：每新建文件需要在父模块手动声明 `mod foo;`，纯样板代码，容易遗漏导致"找不到模块"的困惑错误
2. **可见性标注过多细粒度选项**：`pub`/`pub(crate)`/`pub(super)`/`pub(in path)`，大部分项目只用得到其中两三种
3. 循环依赖没有语言层面的强制约束，容易导致架构腐化

## 采纳方案

### 模块 = 目录自动发现

```
src/
├── main.lv
├── user/
│   ├── model.lv       // 自动归属 user 模块，无需声明
│   └── service.lv
└── order/
    └── handler.lv
```

```lv
// main.lv —— 直接按目录路径导入
use user::model::User;
```

### 可见性三级简化

| Leaves             | 等价 Rust  | 场景                |
| ------------------ | ---------- | ------------------- |
| （默认，无修饰符） | private    | 仅本目录/模块内可见 |
| `pub(root)`        | pub(crate) | 整个包内可见        |
| `pub`              | pub        | 对外部包公开        |

砍掉 `pub(super)`、`pub(in path)` 等细粒度变体。

### 依赖规则：同目录自由，跨目录强制 DAG

```
src/user/
├── model.lv     // 可互相 use 对方
├── service.lv   // 二者循环引用合法（同一"文件组"）
└── mod.lv       // 定义该目录对外导出接口

src/order/
└── handler.lv   // 若尝试循环引用 user 目录 → 编译期报错
```

### 规则细节

- 目录内部文件视为同一逻辑单元的拆分，允许自由互相引用
- 目录之间严格强制 DAG，检测到循环时输出完整依赖链路径：

```
error: 检测到跨模块循环依赖
  user → order → user

  user/service.lv:12  使用了 order::Order
  order/handler.lv:8  使用了 user::User

建议：提取共享类型到独立的 shared/ 模块，打破循环
```

- 该规则的技术价值：模块依赖保证 DAG 后，编译器可以对无依赖关系的模块做真正安全的并行类型检查

## 被否决的备选方案

| 方案                                                            | 为什么被否决                                                                                       |
| --------------------------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| 完全保留 Rust mod 声明机制                                      | 不解决样板代码和"忘记声明"的常见错误，没有体现工程友好的差异化价值                                 |
| 基于显式声明而非文件系统（类TypeScript export，与物理路径解耦） | 牺牲了"目录结构即架构"的直观性，且与查询式增量编译的模块级缓存颗粒度不如目录方案自然契合           |
| 完全禁止任何形式的循环依赖（包括同目录文件）                    | 过于severe，会强迫开发者为本该内聚的几个文件做不必要的拆分，在超大型项目中逼迫引入过多"中间层模块" |
| 保留 Rust 全部可见性细粒度选项                                  | 实践中使用率低，增加学习成本，与简化心智模型的整体目标相悖                                         |

## 影响范围

- 直接决定增量编译的模块级缓存颗粒度设计（DD-006）
- 包管理器 `branch` 的项目结构约定需要与此规则配合
- 编译器需要实现目录扫描 + 依赖图构建 + 环检测算法

## 验证方式

- 参考 Go 语言模块系统的成熟实践（强制无环设计已被 Go 社区广泛验证）
- Phase 3 MVP 阶段实现基础目录扫描与依赖图构建，用真实多模块示例项目验证 DAG 检测的错误信息质量
