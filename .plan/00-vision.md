# 00. 愿景与定位

## 一句话定义

> Leaves = Rust 级别的安全与性能 + 更友好的工程化体验，面向大型软件系统

## 为什么要做 Leaves

### 对标对象的痛点诊断

**Rust 的问题**：

- 生命周期标注心智负担重，`Pin`/`Unpin`/`async` 状态机机制对初学者极不友好
- 编译速度慢，单态化导致代码膨胀，大型项目尤其明显
- 自引用结构体（链表、图）处理极其痛苦，被戏称为"链表问题"
- 异步生态割裂（tokio / async-std / smol 三足鼎立）
- 函数彩色问题：同步/异步代码是两个世界，互相调用处处是坑
- Trait 系统强大但语法噪音大（`where` 子句分散、`impl` 块与定义视觉割裂）

**Go 的问题**：

- GC 停顿不可预测，不适合游戏开发等实时场景
- 缺少真正的泛型表达力（即使有了泛型，仍比 Rust 弱）
- 错误处理繁琐（`if err != nil` 样板代码）
- Channel 不阻止发送后继续修改原数据，隐藏数据竞争风险
- 类型系统缺少代数数据类型（enum + pattern matching 的完整形式）

### Leaves 的回答

不做语义上的颠覆（核心仍是所有权系统 + 静态类型），而是在**工程体验**和**几个具体技术点**上做出结构性改进：

1. **统一的 Region 内存模型**，替代裸 lifetime 标注 + 第三方 Arena 库的拼凑方案
2. **有栈协程 + 结构化并发**，从架构上消灭 Pin/Unpin 和函数彩色问题
3. **Trait 约束内联语法**，去除 `where` 噪音
4. **目录即模块**，查询式增量编译为架构一等公民（非后期补丁）
5. **双轨制运行时**：默认统一运行时（终结生态割裂），高级场景可替换

## 设计哲学（贯穿所有决策的原则）

1. **安全默认，逃生舱始终存在**
   类似 `region<sync>`、`trait Container<Item: multi>`、`grove::spawn_detached` 的命名模式——默认保守安全，需要特殊行为时必须显式标注，且标注本身带有警示性。

2. **显式优于隐式，但不强迫啰嗦**
   取消 `where` 子句、自动推断生命周期，减少样板代码；但关键的性能/安全权衡点（如 `dyn` 动态分发、`dyn_generic`）必须显式声明，不做静默的行为切换。

3. **概念统一优于概念堆砌**
   Region 同时是内存边界和并发边界（scope）；关联类型复用泛型参数语法。尽量减少开发者需要记忆的独立概念数量。

4. **编译器是教学工具**
   错误信息必须包含具体代码路径和可操作建议，而非抽象的理论术语堆砌（这是对 Rust 借用检查器报错体验的直接改进目标）。

5. **架构级问题优先于语法糖**
   增量编译、单态化膨胀等编译性能问题，从编译器架构设计第一天就要考虑，而不是后期打补丁。

## 成功的标志（北极星指标，非量化KPI）

- 一个 Rust 开发者看到 Leaves 代码，**不需要学习新的内存模型理论**，只需要适应语法差异
- 一个曾被 Rust 借用检查器折磨过的开发者，使用 Leaves 处理图/链表结构时**不需要 `Rc<RefCell<>>` 或 `unsafe`**
- 大型项目（10万行+）的增量编译在**修改单个函数体**时，重新编译时间应与项目规模基本无关
- 异步代码和同步代码**可以直接互相调用**，不存在特殊语法边界

## 非目标（Explicitly Out of Scope）

- 不追求比 Python/JS 更快的开发迭代速度（这不是脚本语言的竞争赛道）
- 不追求成为 Rust 的严格子集或完全兼容（可以做 FFI 互操作，但不强求语法/语义兼容）
- 初期不考虑嵌入式裸机场景的极致裁剪（Grove 运行时优先支持桌面/服务器环境）
- 不内置 GC（这是与 Go 的根本分野，不应动摇）
