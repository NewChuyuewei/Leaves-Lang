# Leaves 安全导向开发基线（DO-178C 对齐草案）

**状态：项目内部草案，未批准的认证计划，不构成符合性声明。**

本文响应后续开发采用 DO-178C 思路的要求。当前只建立工程约束和待决事项，
不意味着现有 Lua/Leaves 代码、工具链、测试或发布产物已经满足 DO-178C。
该流程基线文档本身不改变运行时、编译器或语言语义。

## 已确认的采用范围

用户选择：**先提高工程质量，不指定 DAL，不宣称认证。**

当前不是具体机载系统的认证项目。本文中关于 DAL、认证计划、目标机与
独立性等内容是将来若进入该领域时的待决事项，不是当前已落实的要求，
也不意味着普通语言开发必须等待适航批准。

当前开发可以继续，但下一项代码变更应先记录：

1. 需求及唯一标识：解决什么问题，不解决什么问题。
2. 设计和影响分析：涉及哪些源码/API，是否影响 Lua 兼容性、资源和错误行为。
3. 验证用例：输入、预期结果和通过准则，以及需求到代码/测试的对应关系。
4. 实现后的证据：源码版本、工具和构建参数、实际结果、限制及未解决问题。
5. 评审结论：有评审就记录；缺少独立评审时如实注明，不能用 AI 自检冒充独立批准。

以小范围变更开始，不为每次普通修复机械创建完整认证文件集。
只有未来决定建立具体机载项目的安全基线时，才依据系统分配的等级和
批准的计划进一步确定正式保证要求。

## 1. 标准的定位与使用边界

- DO-178C 是机载软件的开发保证指导文件，不是单独的 C 语言编码规范，
  也不是“通过若干单元测试即可获得”的产品认证。
- 软件等级及保证要求应来自系统安全评估和软件分配，不能由语言项目
  自行选择一个等级后宣称可用于该等级的机载系统。
- 本项目不以 SQLite 的测试实践作为 SQLite 或 Leaves 已获得认证的证据。
  参考其他项目的方法不能替代本项目的生命周期数据与验证证据。
- 实际符合性工作需要适用标准的正式文本、合格的项目责任人、明确的
  目标系统及适航/认证协调。本文不是标准目标清单的替代品。
- 在上述事项确定前，本项目使用“安全导向工程基线”这一表述，不使用
  “DO-178C 认证语言”“航空级解释器”或“符合 DAL A”等未经证实的宣传。

## 3. 计划与标准先行

范围明确后，建立并评审适用的生命周期计划和标准，包括：

- 软件认证考虑计划（PSAC）：说明范围、等级、生命周期、符合性方法和协调安排。
- 软件开发计划（SDP）：说明需求、设计、实现、集成与问题处理过程。
- 软件验证计划（SVP）：说明评审、分析、测试、环境、通过准则和独立性安排。
- 软件配置管理计划（SCMP）：说明标识、基线、变更、发布与可重建要求。
- 软件质量保证计划（SQAP）：说明过程监督、审计和偏差处理。
- 软件需求、设计和编码标准：分别约束规范形式、架构与实现方法。

文件拆分或组合方式应由项目计划规定。现有 ROADMAP、README、CI 文件
不能直接视作已经批准的上述生命周期数据。

## 4. 需求与双向追踪

后续进入安全基线的每项变更应先建立可评审的需求，至少记录：

1. 唯一标识、版本、来源和责任人。
2. 输入、输出、状态变化、边界、错误行为及资源约束。
3. 与上层需求、设计及既有 Lua 行为的关系。
4. 验证方法、预期结果、通过准则及证据位置。
5. 需求到设计、代码、测试的正向追踪，以及实现/测试回到需求的反向追踪。

派生需求应单独识别，并按系统过程反馈评估。不得仅给既有测试补上编号，
就宣称完成需求验证；测试结果必须与独立确定的预期结果比较。

## 5. ISO C 编码约束

保留 Lua 的上层风格与底层 ISO C 实现，不改用 C++ 或其他实现语言。
严格 C89/C99 构建是可移植性检查，并非 DO-178C 符合性证据的全部。

进入安全基线的新增/修改 C 代码应：

- 沿用 Lua 的缩进、函数布局、局部声明和注释风格；限制修改范围。
- 明确函数前置条件、返回值、错误路径和调用后的栈布局。
- 涉及 Lua C API 时检查栈容量、绝对/相对索引、可挂起边界及 continuation 状态。
- 分析整数范围、转换、指针生命周期、数组边界、别名和未定义行为。
- 记录分配、GC 可达性、资源关闭和分配失败路径；不假设内存分配总能成功。
- 说明循环、递归、输入尺寸和栈/堆使用的边界；无法证明的界限登记为未解决问题。
- 对 `longjmp`、Lua 错误传播、元方法、协程和动态加载进行显式影响分析，
  不因为它们由上游实现就自动豁免。
- 禁止依靠未说明的 GCC 扩展、未定义行为或跨构建配置的 ABI 假设。
- 安全相关逻辑不能只靠调试断言防护；正式构建仍需定义错误处理。

不在此草案中追溯宣称全部上游代码满足这些约束，也不以 DO-178C 名义
凭空禁止所有动态分配或递归。哪些特性需要限制，应来自目标环境分析和批准的标准。

## 6. 验证与工具证据

每项进入基线的修改按批准的验证计划执行：

- 需求与设计评审、代码评审、数据/控制耦合分析及适用的静态分析。
- 需求驱动的正常范围、边界、鲁棒性、异常与资源故障测试。
- 目标机或有充分依据的代表性环境中的集成验证；宿主 Linux 结果不自动等价于目标机结果。
- 按适用等级确定结构覆盖分析目标，包括适用的语句、判定和 MC/DC 要求；
  覆盖率不能代替需求覆盖，也不能凭空生成缺失需求。
- 对未覆盖代码、停用代码、死代码、无法解释的结果和偏差逐项分析与处置。
- 对不可由源代码验证充分覆盖的目标代码问题，按适用要求开展补充验证。
- 保存测试版本、输入、预期结果、实际结果、环境、运行命令、日志和评审记录。

当前的回归测试、内部断言、ASan/UBSan 和微基准仍可使用，但其作用分别是
回归检查、内部一致性检查、动态错误检测和性能探索；这些工具不能单独证明符合性。
需要评估编译器、测试生成/执行工具、覆盖率工具及静态分析工具对输出的影响，
并根据使用方式与验证措施决定是否涉及 DO-330 工具鉴定，不能一概要求或一概免除。

## 7. 配置管理与变更门槛

进入安全基线的变更应有以下证据，不能仅以“CI 绿色”代替批准：

- [ ] 已批准且可验证的需求，以及相关影响分析。
- [ ] 设计和实现符合批准的标准，例外有记录及处置。
- [ ] 双向追踪完整，问题单与变更相关联。
- [ ] 按计划完成验证和所需独立评审，失败/跳过项有处置依据。
- [ ] 依赖、编译/链接选项、工具版本、目标平台和源码版本可识别。
- [ ] 发布源代码、二进制、生命周期数据及证据之间关系可追踪，可按记录重建。
- [ ] 已知问题及限制明确，发布基线经责任人批准。

若缺少人员、工具、目标环境或正式标准资料，记录为缺口，不伪造批准、
评审独立性、覆盖率或工具鉴定结论。自动生成文档也不等同于人工批准。
